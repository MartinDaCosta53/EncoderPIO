## 1. What the library is

EncoderPIO reads quadrature rotary encoders on the Raspberry Pi RP2040 and RP2350 microcontrollers. Instead of polling the pins in software or taking a pin-change interrupt on every edge, it hands the job of watching the pins to the chip's PIO (Programmable I/O) hardware. The PIO runs a tiny program that samples each encoder's two signals continuously and only involves the CPU when a genuine step has happened.

The library is made up of four files:

| File | Purpose |
|------|---------|
| `EncoderPIO.pio` | The PIO assembly source: the decoder program |
| `EncoderPIO.pio.h` | The assembled program, generated by `pioasm` (not to be edited by hand) |
| `EncoderPIO.h` | The C++ class declaration and public API |
| `EncoderPIO.cpp` | The C++ driver: resource management, interrupt handling and position logic |

## 2. Background: quadrature encoding

A rotary encoder has two outputs, A and B, that produce square waves 90 degrees out of phase. Turning in one direction, A changes before B; in the other direction, B changes before A. The pair (B, A) therefore steps through a Gray-code sequence:

- One direction: 00 → 01 → 11 → 10 → 00 …
- The other direction: 00 → 10 → 11 → 01 → 00 …

Only one bit changes at a time. If both bits change at once, or the state does not change, the transition is either an error (typically contact bounce or a missed sample) or no movement. Comparing the previous state with the current state tells you whether a step happened and in which direction.

Mechanical encoders usually give one full cycle (4 edges) per click, or sometimes two edges per click, which is why the library lets you set how many edges make one position step.

## 3. How the PIO program works

The PIO program remembers the previous reading of the two pins and combines it with the current reading to form a 4-bit number **B'A'BA**, where A and B are the current readings and A' and B' the previous ones. Bit 0 is the A pin and bit 1 the B pin (the B pin is the GPIO immediately after A). That 4-bit number is used as a jump address into a table of 16 entries at the start of the program.

### The jump table

Addresses 0 to 15 of the program are a table. Each entry is a single `jmp` instruction chosen for the transition that the table index represents:

| Index (B'A'BA) | Meaning | Entry |
|----------------|---------|-------|
| 0000, 0101, 1010, 1111 | No change | jump to `read` |
| 0011, 0110, 1001, 1100 | Error (two bits changed) | jump to `read` |
| 0001, 0111, 1000, 1110 | Increment | jump to `send` |
| 0010, 0100, 1011, 1101 | Decrement | jump to `send` |

Because the program jumps to these addresses using `mov pc, isr`, the table must sit at absolute addresses 0 to 15. This is why the program is declared with `.origin 0` and must be loaded at offset 0.

### The main loop

After a short start-up section (`pc_start`), the program loops through four instructions:

1. `out isr, 2`: take the two low bits of the output shift register (OSR), which hold the previous B and A, and put them in the input shift register (ISR), clearing the rest of the ISR.
2. `in pins, 2`: shift the current B and A into the ISR. The ISR now holds B'A'BA.
3. `mov osr, isr`: keep a copy in the OSR. Its low two bits (the current BA) become the "previous" reading on the next pass.
4. `mov pc, isr`: jump into the table at the address B'A'BA.

The table entry then sends the program either back to `read` (nothing to report) or to `send`, which executes `push noblock`. That pushes the ISR, containing B'A'BA, into the state machine's RX FIFO and then wraps back to `read`. The `noblock` option means that if the FIFO is full the value is dropped instead of stalling the program.

The start-up section (`in pins, 2` followed by `mov osr, isr`) reads the pins once before the loop starts, so the first comparison uses a real previous value rather than whatever was in the registers.

### Why the CPU only decodes direction

The PIO program does the hard part, which is recognising valid steps and ignoring invalid ones. It does not distinguish increments from decrements itself. It simply pushes the 4-bit code, and the CPU checks it against two bit masks (see section 5). This keeps the PIO program short and leaves room for the shared jump table.

### Timing

On the no-change path the program takes 5 PIO cycles per sample (out, in, mov, mov pc, jmp). On a path that pushes a step it takes 6. The library calculates the clock divider assuming the worst case of 6 cycles, so the real idle sampling rate is up to 20% higher than the rate requested. By default the target is 1 MHz, which is far faster than any mechanical encoder can change.

## 4. How the C++ driver is organised

### One object per PIO block

Each `EncoderPIO` object controls 1 to 4 encoders on one PIO block, with one state machine per encoder. A PIO block has four state machines, which is where the limit of four encoders comes from. All state machines on an object share a single copy of the PIO program.

A static array `_instances[3]` records which object owns each PIO block (RP2040 has two blocks, RP2350 has three). The interrupt handler for a block uses this array to find its object. This is why only one object may exist for each block.

### Per-encoder state

Each encoder has a `Channel` record containing:

- The A pin and the state machine number
- `position` and `subCount`, both `volatile` because the interrupt handler changes them
- `minPos`, `maxPos` and `wrap` for range handling
- `countsPerDetent`, also `volatile`

### Starting: `initialiseEncoder()`

The start-up sequence is careful to check everything before it changes any hardware, and to undo what it has done if something fails. The steps are:

1. Return `true` immediately if already running.
2. Select the PIO block (`pio0`, `pio1`, or `pio2` on RP2350) and fail on an invalid number.
3. Fail if another object already owns that PIO block.
4. Check that every A pin has a B pin after it that exists on the chip.
5. Check that no two `{A, A+1}` pairs overlap. The test `-2 < difference < 2` catches both the same pin and neighbouring pins.
6. Check that the program can be loaded at offset 0.
7. Claim one free state machine per encoder. If the claim fails part-way, the machines claimed so far are released and the function fails.
8. Load the PIO program at offset 0, once, for all state machines.
9. For each encoder: hand both pins to the PIO, make them inputs, set the clock divider, set the input shift direction to shift left with no autopush, set the output shift to right with no autopull, join the FIFOs so the RX FIFO is 8 words deep (nothing is ever sent to the TX FIFO), and initialise the state machine at the program's start-up entry (offset + 16, just after the jump table).
10. Apply the pull-ups.
11. Register the object in `_instances[]` and enable the "RX FIFO not empty" interrupt source for each state machine on PIO IRQ line 0.
12. Add the shared interrupt handler for that PIO block and enable the interrupt.
13. Enable all the state machines.

Only after all of this does it set `_initialised` and return `true`. The checks happen before anything is claimed so a failed start leaves the chip untouched.

### Stopping: `end()`

`end()` reverses the start-up in a safe order:

1. Disable each state machine and its interrupt source first, so no new data can arrive.
2. Remove the handler, and disable the system interrupt only if no other code is sharing it.
3. Clear the `_instances[]` slot.
4. Return the pins to plain inputs with the pulls off.
5. Clear the FIFOs, unclaim the state machines and reset each `subCount`.
6. Remove the PIO program from the PIO block.

Positions and settings are kept, so calling `initialiseEncoder()` again resumes from the same configuration. The destructor calls `end()`, so an object going out of scope cleans up after itself.

## 5. Interrupt handling and position counting

### Servicing the FIFOs

Each PIO block has its own static handler (`pio0_irq_handler`, `pio1_irq_handler`, `pio2_irq_handler`). It looks up the owning object in `_instances[]` and calls `serviceFifos()`. That function loops over every encoder on the object and empties its RX FIFO. The interrupt stays asserted while any FIFO has data, so the handler drains them all.

For each word, the lower four bits are examined against two masks, with bit *n* set if code *n* is a step in that direction:

- Decrement codes: 0010, 0100, 1011, 1101 (`DEC_MASK`)
- Increment codes: 0001, 0111, 1000, 1110 (`INC_MASK`)

A single shift-and-test on the mask tells the handler the direction without any lookup table or branching on individual values.

All the handler code and the counting routines are placed in RAM (`__not_in_flash`), so reading or writing flash from the other core cannot delay them.

### Counting detents

Each step calls `incPos()` or `decPos()`. These do not move the position straight away. They add or subtract one from `subCount` and only move the position when `subCount` reaches plus or minus `countsPerDetent`, at which point `subCount` resets to zero. Two things follow from this:

- Encoders that produce 2 or 4 edges per click only change position once per click.
- If the encoder reverses direction part-way through a click, the partial edges cancel out, so there is no flicker between neighbouring values.

When the position moves, it respects the limits. At a limit the position either stays put (`wrap` false) or jumps to the opposite limit (`wrap` true).

## 6. Public API behaviour

- **Encoder index.** Methods take an index in constructor order. For a single encoder the index can be left out, so single-encoder code needs no changes.
- **Bad indices.** Invalid indices never crash: getters return 0, setters do nothing, and `setLimits` returns `false`.
- **Thread safety with the interrupt.** `setPosition`, `setLimits` and `setCountsPerDetent` briefly disable interrupts while they change several related values together, and they reset `subCount` so a stale partial detent cannot carry over. `getPosition` reads one `volatile int` and needs no lock.
- **Limits.** `setLimits` rejects `maxPos <= minPos`, and clamps the current position into the new range.
- **Counts per detent.** Values below 1 are treated as 1 and values above 100 as 100. The cap keeps `subCount` (an `int8_t`) from overflowing but realistically the value is most likely to be 1, 2 or 4.
- **Pull-ups.** On by default, and can be changed before or after start-up. Pull-downs are never used.
- **Sample rate.** `setSampleRate()` recalculates the divider as `clk_sys / (rate × 6)`, clamped to the PIO divider range of 1 to 65535, and updates running state machines immediately. If the system clock changes later, call it again.

## 7. Design decisions and limitations

| Decision | Reason |
|----------|--------|
| Hardware decoding in PIO | No missed edges, minimal CPU load, immune to interrupt latency |
| Jump-table decoder | Constant execution time and invalid transitions ignored without extra code |
| Direction decided by the CPU | Keeps the PIO program small and the table at address 0 |
| B pin fixed at A + 1 | Lets one `in pins, 2` read both signals at once |
| Program loaded once at offset 0 | The jump table needs absolute addresses; all state machines share it |
| One object per PIO block | The interrupt handler and `_instances[]` slot are per block |
| `push noblock` | The program never stalls if the CPU falls behind; steps are dropped instead |
| Check-then-claim start-up | A failed start leaves no resources half-allocated |
| Sub-detent counter | Handles different encoder types and removes jitter on direction changes |

Limitations to be aware of:

- The PIO instruction memory at offset 0 must be free, so the library cannot share a PIO block with a program that already starts there.
- The B pin must be the GPIO after A.
- The handler runs on the core that called `initialiseEncoder()`, so start and stop the encoders on the same core.
- If the CPU does not service the FIFO in time (8 words deep per encoder), steps are lost.
